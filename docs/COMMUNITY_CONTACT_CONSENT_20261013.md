# 社群管理员申请联系授权 · 2026-10-13

本次从个人 integration `3d819038c96e9cc8a09ee5103d238d66cba9d5b9` 建立独立 `codex/community-contact-consent-20261013`，只调整现有管理员申请、修改重提和批准前的联系授权门槛。网站和原生小程序已有同一入口；无需新 API、collection 或迁移，原生版本保持 0.3.1。

用户确认的新规则为：

- Checkbox 文案：**我同意展示我的微信名片作为进群联系方式**。
- 未明确同意时提示：**由于入社流程规定，必须展示管理联系方式**。

新申请默认不勾选。历史 `false`、`null` 或缺失值保持未勾选；既有 `true` 仅回显申请人原来保存的授权，不从其他角色、任职或资料推定同意。提交按钮允许用户点击获得提示，不通过无说明禁用掩盖原因。

## 两端行为

网站提交时先检查同意，显示关联 Checkbox 的 `role=alert`、`aria-invalid`、可访问说明并聚焦/滚动定位；其它已有字段继续原校验。服务器同意错误也回到该字段，失败不重置文字或已选文件。原生申请页显示同一提示及读屏标签，渲染后在仍有效的页面/账号/操作上下文定位同意区域；未同意时无 POST、无写入锁，不自动勾选或重发。两端保留弱网、重复点击、修订冲突和原隐私授权流程。

已批准名片的本人更新/关闭展示设置继续允许 `false`。本次申请门槛不改为所有名片强制公开，也不修改既有角色、社群任职、私有答卷能力或进群状态。查看二维码、提交或批准申请仍不表示已经进入微信群。

## 服务端权威

网站 Server Action 只将 Checkbox 的明确 `on` 值转换为布尔 `true`；小程序 JSON 申请和重提入口只接受原始布尔 `true`。Collection `beforeOperation` 在 Payload 的 Checkbox 字符串转换及旧字段合并前再次核验原始输入：`false`、缺失、`null`、`"true"`、`"false"`、数字、对象和数组都不能提交。

本人重提服务先核验现有身份、归属与 revision，再要求明确布尔 `true`；已有记录的旧 `true` 不能在请求省略字段时经合并绕过。撤回及本人已批准名片更新使用原动作/权限，未被强制展示规则覆盖。

批准服务及 Collection 再读取当前原申请的 `contactConsent === true`，不接受审核人通过请求补授权。展示仍要求已批准申请、有效任职和对应展示授权，仍只走现有受控联系投影；原始姓名、手机号、说明及二维码读取权限保持。

## 历史申请的精确影响

没有生产读取、存量迁移或批量授权。历史 pending 申请的 `false`、`null`、缺失值不能批准：服务端返回 409，页面解释原因，并保留退回/拒绝动作。负责人应退回，由申请人从既有“修改并重新提交”入口主动勾选；同一申请编号保留，按新 revision 再审核。审核人不能改申请人同意或绕过旧记录补齐。

历史 true 仍可按现有完整资料、有效账号及当前权限审核。已批准但隐藏的历史名片不自动公开，既有未授权用户不被代授权。后台列表和旧客户端即使仍显示批准动作，服务器也会复核并拒绝未经同意的记录。

隐私正文与 draft/editing CMS JSON 仅同步上述申请授权句子，运营者、`yejx2003`、报名 1 年、成员长期和人工删除安排保留；只读保留工具逐文件未改，没有写入运行中的 CMS。
