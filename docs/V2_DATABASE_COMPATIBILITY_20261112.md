# V2 旧数据库兼容与无损升级核验（2026-11-12）

## 结论与适用边界

新版网站与原生小程序共用现有 Payload/PostgreSQL 后端及账号、报名、申请、队伍、内容和媒体记录，无需重新建库或导入演示数据。通过审查后的增量迁移可以保留已测历史基线的业务数据。**本报告验证的是隔离合成旧库，未连接生产数据库、未部署，也不能承诺任意未知旧库都可直接升级。**

核验开始时，GitHub `new` 的实际提交为 `dd3aad4b71c85f34ad96d0b49a6f1dd80c7fbfeb`，tree 为 `214389cbcd363c3aad9074a6e0d6208cb2bd51e0`。本地 HEAD 仍为 `58f0de98b349ab13343780a4e05f2d6d55249cef`，但暂存树与远端 tree 完全相同、工作树无额外差异。此次工作保留原暂存内容，没有重置、切换、提交或推送分支。

### 本轮修复

1. `src/lib/v2/shared.ts`：旧公开媒体的 URL 可能为绝对地址。原 V2 投影仅接受相对 URL，导致数据库和图片仍在，但封面/相册图片在新版中消失。现在从合法文件名生成同源 `/api/media/file/<filename>`，继续经过 Payload 文件权限及已配置存储适配器；不修改旧 URL、文件名、文件内容或 S3 对象，不把外部直链放入列表响应。没有文件名时仅接受本站媒体文件接口 URL。禁止私有目录、路径分隔符、控制字符和 SVG 等不支持的文件名。
2. `20260926_145257_nickname_login`：对于**从未执行该历史迁移**的数据库，保留旧 `users.account` 数值账号及唯一索引，只解除 NOT NULL，让新账号无需填写旧字段。旧列是保留档案，不重新启用数字账号登录；新版使用昵称/邮箱。Payload 3.90.1 按 `payload_migrations.name` 跳过已执行迁移，没有文件校验和重放机制，已执行数据库不会再次运行该文件。**历史版本已删除的 account 列不会自动恢复，若需找回只能从当时备份核验。** 不手工删除迁移记录，不重跑旧迁移。

后续生成迁移也须保留该未映射历史列；不要使用自动 schema push 清理“多余”列。

## 数据保留与行为差异

- 11 月新增迁移为扩展式：发布图片 JSON、社群日程、临时上传记录和 V2 主场区块。旧记录新字段为空，旧社群帖子不会被猜测时间地点。
- 旧 `site.modules` 保留，但 V2 使用独立的 `homeSections` 默认区块。旧区块的禁用/排序不自动变成 V2 设置，上线前由运营确认新版区块。
- 旧队伍、赛季名单和荣誉仍在；历史名单不自动成为新版受审核的有效队员，未同意公开的资料继续隐藏。
- 旧聊天、论坛、评论和点赞数据表保留，功能仍关闭。数据存在不意味着重新开放入口。
- `pending_uploads` 的外键保留所有者：未处理的上传引用可能阻止删除账号，不应通过级联删库消除限制。
- 保留现有 `PAYLOAD_SECRET`、数据库连接、媒体挂载、S3 配置及账号身份；不要为了部署重生成秘密或挂到空媒体目录。

## 获得部署授权后必须执行的备份与升级步骤

1. **先只读盘点**：核对运行中的代码 SHA、数据库引擎版本、迁移台账、实际列/表/索引、业务行数、旧数字账号是否仍存在、昵称有效性/大小写重复、队伍保留路径冲突。确认存储是本地还是 S3、所有私有视频目录及实际挂载。遇到 `payload_migrations.batch=-1`、缺失迁移记录、重复/半完成结构或手工 schema 修改，停止自动迁移，先在副本审查。不要接受 Payload 关于动态 schema push 可能丢数据的继续提示。
2. **停止写入而非删除数据**：维护窗口暂停所有网站、小程序、后台和作业的写入口，保留旧应用镜像与完整配置。保存迁移前行数/内容哈希及迁移台账。只备份数据库而继续接受上传无法保证一致性。
3. **做可验证的完整备份**：使用与数据库兼容的 PostgreSQL 17+ 客户端导出 custom-format 数据库；完整备份普通媒体和本地 `.showcase-videos`、`.showcase-videos/.team-honor-reserved`、`.team-honor-videos`。S3 模式须先取得完整对象镜像/版本清单，再以 `MEDIA_BACKUP_SOURCE` 纳入；S3 不能代替额外的本地私有视频备份。保留环境配置的安全副本及旧 `PAYLOAD_SECRET`，不写入仓库或普通日志。
4. **禁止顺带清理历史备份**：现有 `scripts/backup.mjs create` 含保留期删除逻辑。部署备份使用全新、空的独立 `BACKUP_DEST`，不指向已有备份目录；任何已有文件或备份清理，尤其两台新 Xfusion 工作机上的清理，必须另得用户批准。不要调用 `migrate:fresh`、`migrate:reset`、`demo:clean`、`seed:demo` 或 `DB_PUSH=true`。
5. **先验证恢复再升级**：将完整备份恢复到新的隔离库和隔离媒体目录，以 manifest 校验所有业务表、媒体哈希、私有视频和隔离标记；核对数据库 dump 哈希及序列。留存异机备份并验证可读取，不只看“备份成功”日志。生产源保持不变。用待发布代码在该副本上执行迁移并进行旧账号登录、报名/申请历史、网站/小程序鉴权、图片/视频和权限抽查。
6. **只执行缺失的迁移**：确认恢复演练和权限检查通过后，生产保持 `DB_PUSH=false`，按现有顺序运行 `pnpm migrate`，保留台账；不要为实现“幂等”到处添加 `IF NOT EXISTS` 来掩盖漂移。锁超时/失败时先查事务和台账再重试，不跳过失败迁移。
7. **比对后放行**：原业务字段逐表计数/哈希与备份一致，仅允许审核过的新增字段和回填；检查网站与小程序的 API、既有用户登录、原报名与申请、公开/私有媒体、成员同意和账号状态。确认没有空媒体卷/错桶后恢复写入。

## 回滚约束

优先回滚到已在升级库副本验证兼容的旧应用构建，**保留扩展结构和所有新旧数据**。11 月迁移及主要运营迁移的 `down()` 明确拒绝删表/删列，不应绕过。

若需要完整恢复迁移前备份，应先保留升级后的数据库和媒体；恢复到新的库/目录验证后再切换，不能覆盖唯一数据副本。恢复旧备份会遗漏升级后产生的新报名、申请和内容，必须先冻结写入、导出并核对这部分增量；涉及数据舍弃或旧文件清理时另行取得明确授权。旧应用与更早角色/生命周期规则的兼容性需按具体回滚版本复查，不能把“代码能启动”视为权限安全。
