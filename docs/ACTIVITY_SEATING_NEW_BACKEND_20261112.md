## 网站与小程序共用接口

基地址：`/api/activities/{kind}/{id}/seating`，`kind` 为 `events` 或 `community-posts`，`id` 为正的 PostgreSQL integer ID。

| 方法 / 路径 | 输入 | 返回及权限 |
| --- | --- | --- |
| GET 基地址 | 无 | `SeatingState`：座位图、占用状态、open/enabled、本人最新申请与未提交凭证 ID；站点活动匿名可读，不含他人手机号、名字或凭证。社群活动须登录，与 new 社群详情一致。 |
| GET `?mode=review&status=pending&page=1` | status 为 pending/confirmed/rejected；每页20条 | `SeatingWorkbench`：审核者可读姓名快照、电话、凭证 ID、状态；含 hasNextPage。 |
| PUT 基地址 | `{enabled:boolean}` | `{enabled}`，有审核权者启停。停用不删除历史，不妨碍继续审核。 |
| POST 基地址 | `{seats:string[],phone:string,proofs:string[]}` | `{mine:SeatRequest}`；返回本人申请，不回显手机号/凭证内容。若本人已存在待审核/已确认申请，重试返回该原申请，不改座、不新增。 |
| POST 基地址 | `{action:"review",id:number,status:"confirmed"\|"rejected"}` | `{status}`；重复同一决定幂等，不允许把已处理申请换成另一决定。驳回与释放座位在同一事务中。 |
| POST `/proofs` | multipart，单个 file | 201 `{id:UUID}`；输入限静态 JPEG/PNG/WebP、8MiB，按原规格归一化为1600px以内WebP，存储最多2MiB。 |
| GET `/proofs/{UUID}` | 有效会话 | WebP二进制；本人可读本人的有效草稿及已提交凭证，审核者只可读本活动已提交凭证。不要改用公开媒体/V2图片票据接口。 |
| DELETE `/proofs/{UUID}` | 有效会话 | `{removed:true}`；只移除本人该活动未提交草稿，不删除已提交凭证。 |

固定12排381座，每份申请1–10个不同有效座位，1–10张不同的有效本人凭证，每人每场最多一份待审或已确认申请。上传草稿有效期24小时；被驳回后可重新申请。请求/响应类型位于 `src/lib/activity-seating-model.ts`。

### 鉴权及特殊状态

- 浏览器写入须携带同源 Origin；原生小程序携带 `Authorization: JWT <token>`，若另带 Origin 也须同源。
- 任何显式 Authorization 都不得回退 Cookie 身份；未知格式直接401，JWT本身仍由Payload验证。有效JWT优先于环境Cookie。注销、封禁及撤任后的新请求不能沿用旧权限。注销不承诺取消已通过鉴权的在途操作；锁内重新核对账号/任职，不重新校验每个会话ID。
- 审核权限**保持 main 选座独立合同**：社长/副社长，或活动关联社群的 active 任职。即使 viewSignups/exportSignups 等能力为false，active任职仍可审核选座；此规则不会扩展已有报名问卷读取/导出权限。未关联社群的站点活动只由社长/副社长审核。
- new 社群活动检查所属社群的 published/demo 可见性，并按新增的 endAt 截止。社群匿名401；隐藏活动或不可见父社群404；结束、停用、抢座/凭证冲突409。站点活动仍遵守 new 原站点公开活动规则，不因可选的游戏关联隐藏而自动隐藏该站点活动。
- 401/403时前端应清空私有审核列表及凭证缓存；409时重读状态，不假定本地选中仍有效。预约者停用页面后仍可能有已提交记录，不应清除服务端申请。
- JSON未知字段、伪造身份/状态字段、重复或无效座位、跨人/跨活动/过期凭证均拒绝；其他主要状态：400字段无效、413请求过大、415类型不支持。不可把内部数据库错误细节回显给用户。
- 所有响应 private/no-store、Vary Cookie/Authorization；凭证附加 same-origin 资源策略。小程序使用带JWT的下载方法，不把私密凭证URL当公开图片链接。

## 并发与权限复核

同一选座设置行 FOR UPDATE 串行化申请、上传、审核；数据库同时保留座位 `(seating_id,seat)` 唯一约束和每会员有效申请的部分唯一索引。

写入事务对当前账号、活动及关联社群加 FOR SHARE，随后使用**同一数据库连接**重新读取账号状态、平台角色、有效任职、活动发布及结束时间。这样既不会按等待锁之前的旧状态写入，也不会因每个事务又借一个Payload池连接而在高并发时耗尽连接池。发生锁超时、死锁、序列化或唯一冲突，返回409供客户端重读。

这不是无条件“取消已开始的操作”：先取得锁的合法操作可能先完成，后续撤权/停用等待它提交；如果撤权/结束事务先持锁，选座会等待并读取其提交后的状态。本轮实际测试了后一种情况。

## 部署与回滚边界

生产执行仍须先取得部署授权，按 `V2_DATABASE_COMPATIBILITY_20261112.md` 只读盘点、冻结写入、完整数据库及本地/S3媒体备份、隔离恢复并验证后才迁移。手机号码与凭证在数据库里，数据库dump必须覆盖这四表；不要只备份普通上传目录。

迁移本身只新增结构，不删既有业务记录，down明确拒绝删除数据。**但不应宣称永久保留所有选座数据**：main原外键合同保留了删除活动/账号时的级联；服务原合同也会清理过期草稿、提交后未使用草稿，成员可主动移除未提交凭证，驳回释放占座。此次未对真实数据执行任何这些操作。删除活动/账号或清理已提交记录仍需符合既有权限及明确授权。

优先回退经过升级库验证的旧应用并保留扩展结构。完整恢复旧备份会漏掉升级后申请，必须先保留升级后库及核对增量，禁止覆盖唯一副本。真实生产schema/记录、S3实物、数据库dump/restore、部署、最终浏览器及微信原生验收均不由本次合成后端测试替代。
