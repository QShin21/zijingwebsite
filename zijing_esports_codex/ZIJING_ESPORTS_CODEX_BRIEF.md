## 2. 产品定位与基本原则

网站服务于四个目标：让访客了解社团；让同学找到活动与加入方式；保存代表队及社团历史；让不写代码的骨干可以持续运营并完成换届交接。

首页是入口，不是所有内容的堆积页。网站的长期价值来自稳定的信息结构、结构化内容、真实资料、权限边界和运营后台。

默认条件如下。除非工作区已有明确约束或用户另行指定，采用这些条件直接推进，不要逐项等待确认。

| 项目 | 默认决策 |
|---|---|
| 语言 | 简体中文为主，文本结构保留未来多语言扩展可能；V1 不实现多语言系统 |
| 访问者 | 以校内学生为主要受众，同时允许外部访客浏览公开内容 |
| 设备 | 手机优先，同时适配桌面和微信内置浏览器 |
| 品牌 | 使用用户提供的社团名称；以紫色识别、校园真实感和适度竞技感为方向 |
| 运营方式 | 骨干通过后台维护，新增日常内容不需要修改代码 |
| 公众账号 | V1 不要求访客注册，不开发会员社交体系 |
| 报名 | V1 使用后台可配置的外部报名入口，站内申请与审核留到后续版本 |
| 架构 | 单仓库、模块化单体，不使用微服务 |
| 扩展 | 内容模型、页面组件、业务模块可扩展，不开发通用低代码平台 |
| 事实边界 | 不编造社团历史、荣誉、阵容、学校授权、活动、人数或合作伙伴 |

学校名称、标识、域名、对外称谓和校代表队身份，均以用户提供且获准使用的资料为准。不得因项目名称而自行声称本网站是学校官方门户或某支队伍是校级代表队。

## 3. 技术方案与工程约束

### 3.1 默认技术栈

- Next.js App Router + TypeScript。
- Payload CMS，尽量与 Next.js 放在同一个应用和仓库中。
- PostgreSQL，使用 Payload 适配器和对应迁移机制，不再引入另一套 ORM 竞争管理同一组表。
- Tailwind CSS + 集中的设计变量 + 可复用组件。
- 优先采用与当前所选版本兼容的成熟组件与认证能力，不自行发明加密、会话或密码存储方案。
- 单元和集成测试优先使用 Vitest 或兼容测试工具；端到端测试使用 Playwright。
- Docker Compose 管理部署；新部署可用 Caddy，已有 Nginx 的环境优先安全接入，不为新网站替换整个现有服务。
- 本地开发使用持久化媒体目录；生产支持适合实际部署区域的对象存储适配。所有媒体接口必须通过统一存储配置，不把业务代码绑定到某一云厂商。

开工时自行核验 Node.js、Next.js、Payload、数据库适配器和其他核心依赖的兼容性、安全维护状态及实际文档。选择相互兼容的受维护稳定版本，固定版本和锁文件。不得机械使用本文编制时的假定版本，也不要未经验证盲目追随最新主版本。

优先使用 pnpm 并固定 package manager 版本。已有成熟项目时应遵循其实际包管理体系，避免生成多套锁文件。

### 3.2 既有项目与新项目

先检查目录、Git 状态、现有项目、环境文件和已有运行服务。仅盘点本项目所需范围，不读取无关私人资料或其他项目密钥。

空目录按本方案初始化。已有兼容项目就增量完善。已有不同但可用技术栈时，先评估复用与迁移成本；不得为了套用模板直接删库重建或覆盖已有业务。重大且不可逆的架构迁移需要明确提出，但不妨碍先完成安全的独立部分。

### 3.3 工程目录与边界

具体目录可按当前框架最佳实践调整，但必须能够辨认出以下职责：

```text
src/
  app/                 公开网站、后台接入及接口路由
  components/          复用界面组件与页面模块
  collections/         CMS 内容模型
  globals/             站点全局配置与固定页面配置
  access/              角色、字段、对象级访问控制
  lib/                 内容查询、日期、链接和存储等公共逻辑
  migrations/          数据库迁移，位置以适配器规范为准
scripts/               初始化、检查、备份与部署辅助脚本
tests/                 单元、集成和端到端测试
docs/                  产品、架构、运维、验收和进度
```

公开展示使用显式筛选和最小字段集合，不把后台原始对象直接传到浏览器。不要创建重复的数据模型和多套互不一致的查询逻辑。

## 4. V1 公开网站范围

### 4.1 栏目与路由

下列是建议路由，可为已有项目做等价调整，但不得遗漏业务能力。

| 页面 | 路由 | 要求 |
|---|---|---|
| 首页 | `/` | 后台驱动的社团入口，详见下一节 |
| 关于我们 | `/about` | 简介、组织结构、发展历程、文化与常见问题 |
| 活动列表 | `/events` | 按时间、类型、游戏项目筛选，分页与空状态 |
| 活动详情 | `/events/[slug]` | 时间、地点、条件、报名入口、详情、回顾和相册关联 |
| 代表队列表 | `/teams` | 按游戏项目展示公开代表队 |
| 代表队详情 | `/teams/[slug]` | 介绍、赛季、获准公开的阵容、相关活动与荣誉 |
| 荣誉档案 | `/honors` | 按年份、项目和代表队筛选，明确信息来源 |
| 荣誉详情 | `/honors/[slug]` | 赛事、日期、组别、名次、关联队伍与公开证明来源 |
| 加入入口 | `/join` | 普通社员、代表队选拔、骨干招新三个入口 |
| 普通社员招新 | `/join/members` | 说明与对应招新批次 |
| 代表队选拔 | `/join/teams` | 项目、条件、安排与对应批次 |
| 骨干招新 | `/join/staff` | 部门、岗位、职责、投入要求与对应批次 |
| 招新批次详情 | `/recruitment/[slug]` | 本批次专属条件、起止时间、报名入口、联系人和归档状态 |
| 动态列表与详情 | `/news`、`/news/[slug]` | 公告、新闻、回顾和人物故事 |
| 影像列表与详情 | `/gallery`、`/gallery/[slug]` | 按活动或主题归档的相册 |
| 联系与合作 | `/contact` | 经过确认的公共联系方式与合作渠道 |
| 隐私说明 | `/privacy` | 按实际功能展示的数据处理说明；未经确认的法律文本不得伪称已获审核 |
| 基础页面 | 404、错误页等 | 友好错误、加载与空数据状态，返回路径清楚 |

页眉导航保持简洁，重点入口为“加入紫荆”。联系、隐私、相关社交账号等可进入页脚。不得制造只有图标却没有可访问名称的链接。

历史内容使用稳定 slug。标题修改不应自动破坏既有链接；如运营人员明确修改已发布 slug，应记录旧路径并重定向。历史招新、赛季和活动不得被新一轮内容直接覆盖。

### 4.2 首页

首页包括以下模块：社团品牌首屏、当前重点、三类加入入口、近期活动、代表队与精选荣誉、社团生活、简介及联系方式。

后台应能编辑首屏标题、副标题、图片、按钮，配置重点内容，并启用、停用或调整预设模块的顺序。采用受约束的模块集合，不开发任意执行 HTML/JavaScript 的页面编辑器。

近期活动、最新动态等来自数据库；推荐内容可以手动指定，也可按规则自动选择。必须避免重复卡片、失效推荐和空白模块。

推荐规则只读取符合公开条件的记录。活动和报名临近截止时，页面展示须随时间正确变化；不能只在内容保存时计算一次状态。

没有活动或荣誉时使用真实空状态或隐藏相应模块，不制造虚假记录填充版面。没有经过核实的统计数据时不显示“社员数”“获奖数”等宣传数字。

### 4.3 手机、微信内置浏览器与无障碍

至少覆盖 360、390、768 和 1440 像素宽度的检查，适配实际视口和长中文标题。不要只缩放桌面布局。

二维码不能是唯一参与方式。提供可点击链接、可复制的文字信息或清晰的替代说明。不得让手机用户只能使用另一台设备扫码。

保证基础键盘操作、可见焦点、合理对比度、语义化标题、图片替代文字和减少动画选项。主要公开页面不能依赖 hover 才能操作。

优先使用真实且授权的活动图片。缺少图片时采用文字、布局和明确占位，不擅自抓取游戏版权素材、学校标识或人物照片。禁止未授权素材和演示人物被误认为真实社团成员。

不默认加入自动播放视频、粒子背景、鼠标拖尾和高频闪烁。动态图形不能妨碍阅读。关键资源不依赖可能无法稳定访问的外部字体或脚本 CDN。

## 5. 内容模型与业务规则

### 5.1 最低内容模型

可根据当前 CMS 能力采用 collection、global 或内嵌结构实现，但必须保留下面的信息关系。

| 对象 | 主要信息 | 关键规则 |
|---|---|---|
| 后台用户 | 身份、角色、负责的分部范围 | 非公开，不等同于社员数据库 |
| 游戏项目 | 名称、slug、获准使用的图标、介绍、排序 | 作为统一分类，不在各页面重复写字符串 |
| 代表队 | 项目、名称、介绍、封面、公开状态 | 不自行声称校级代表队身份 |
| 赛季阵容 | 代表队、赛季、获准公开的成员展示信息和位置 | 按赛季保存，不覆盖历史，不储存无关私人信息 |
| 荣誉 | 标题、赛事、组别、名次、日期、队伍/赛季、公开来源、核验状态 | 公开展示必须同时满足发布条件和已核验条件 |
| 活动 | 标题、slug、类型、项目、时间、地点、条件、报名窗口、入口、正文 | 内容发布、活动生命周期、报名状态分别建模 |
| 动态文章 | 标题、类型、摘要、正文、封面、发布日期、关联活动/队伍 | 草稿预览与正式发布分离 |
| 招新批次 | 类型、名称、条件、岗位或位置要求、起止时间、报名渠道、联系人 | 一次招新一条批次记录，历史永久链接保留 |
| 相册 | 名称、说明、日期、关联活动、图片及替代文字 | 与公开媒体关联，按主题长期归档 |
| 公开媒体 | 文件、尺寸、说明、替代文字、来源/授权备注 | 只放获准公开的媒体，不接收私人申请附件 |
| 站点配置 | 社团名称、导航、页脚、联系方式、SEO 默认值、首页模块 | 运营修改不需要改代码 |
| 固定内容页 | 关于、联系、隐私、加入介绍等 | 后台可维护，使用受约束的内容模块 |
| 重定向与审计记录 | 路径变更；关键管理操作的时间、操作者、对象 | 不记录秘密或不必要的个人信息 |

推荐常用字段：标题、slug、摘要、封面、正文、分类/关联、发布时间、排序或置顶、SEO 信息、创建/修改时间、发布与归档状态。不要无差别地把所有字段强加给每个对象。

当前代表队阵容可以从最新有效赛季读取，但旧赛季必须可以查询。荣誉应关联取得成绩时的队伍/赛季，不应因为现役阵容变化而改变历史归属。

非公开荣誉证明材料在 V1 不进入公开媒体库。可以保存后台核验记录和公开出处；确需非公开文件时应使用独立鉴权存储，不得依赖“界面上没放链接”实现保密。

### 5.2 状态、日期和截止规则

明确区分：

1. 内容状态：草稿、已发布，以及是否归档。
2. 活动生命周期：计划、取消、延期、结束等；时间与人工状态有明确优先级。
3. 报名状态：未开始、开放、已截止、人工关闭，以及有无有效入口。

招新和活动入口只有同时满足公开条件、有效时间窗口、未人工关闭且入口有效时，才能显示为可报名。截止后保留详情和历史信息，移除或禁用当前报名 CTA。

时间统一存储为 UTC，后台输入和前台展示按 `Asia/Shanghai` 处理，并使用支持时区的可靠工具。对跨天、截止边界、无截止时间、取消和延期编写测试。

外部平台是否仍在接受提交不由本站控制。后台应显示“最近核验入口时间”，运营文档中说明需要同步关闭外部表单；不得声称本站已截止就能阻止所有外部提交。

### 5.3 内容复用

活动详情关联回顾文章和相册；新闻关联活动或代表队；荣誉关联队伍及赛季；首页引用现有记录。

不要为首页、列表和详情分别维护三份相同活动信息。不要把内容字段直接写进 React 组件中。

## 6. 招新与报名：V1 的明确实现方式

V1 必须完整实现三类招新页面、批次管理、岗位/位置介绍、时间状态、入口配置、联系方式和历史归档。

报名渠道支持普通 HTTPS 外部表单链接，以及经过确认的群号、二维码或公共联系方式。缺少有效渠道时，不伪造链接，不把按钮指向 `#`，不显示虚假“提交成功”。

不同类型可以使用不同的说明与内嵌岗位结构，但共用批次、时间和入口等基础能力。骨干岗位应能说明职责、要求、工作量预期及申请方式；代表队选拔应能说明游戏项目、位置需求、参加条件和选拔安排。

V1 不保存申请人的私人资料，不开发公众注册、站内申请表、面试审批、短信通知或收费功能。这些功能在后续版本确有需要时另行实现。

代码模块保留扩展接口，但不要建立一套没人使用的申请表、审核表和会员表来“预留”。将未来模型和迁移思路写入路线图即可。

## 7. 后台、权限和发布流程

### 7.1 V1 后台能力

后台应有中文标签、清楚的字段帮助、必填校验和友好错误。运营人员应能完成草稿保存、预览、审核发布、撤下、归档及可用范围内的版本恢复。

已发布内容的编辑不能因为普通编辑员点击保存就越过审核自动改变正式页面。草稿和发布版本的行为要通过真实测试确认。

后台可以维护站点主要内容和首页，但不能任意插入脚本、修改应用代码或自行开放服务端权限。

### 7.2 最低权限角色

| 角色 | 范围 |
|---|---|
| 系统管理员 | 账号、角色、站点设置、内容与系统管理 |
| 内容编辑 | 编辑获授权内容的草稿，不能管理账号或越权发布 |
| 发布负责人 | 审核和发布获授权的公开内容，不能随意提升自身系统角色 |
| 分部负责人 | 维护被分配分部的介绍、赛季阵容及相关荣誉草稿 |

后续站内报名上线时再增加招新审核权限。本版没有私人申请数据时，不制造一个空的审核系统。

角色组合、分部范围和字段权限必须统一处理。用户不能通过提交 `roles`、`teamIds`、`status` 或嵌套关系等字段提升自身权限。

### 7.3 权限实现要求

权限在服务端执行，覆盖后台、REST/其他开放接口、Local API 调用、预览、关系展开和文件访问。隐藏菜单不是权限控制。

核验所采用 Payload 版本的 Local API 权限默认行为。面向用户或公开请求的路径必须明确启用访问控制，并传递正确的身份上下文；公开请求不得继承后台管理员身份。确需内部特权调用时，集中封装、记录原因并测试。

公开查询必须排除草稿、未核验荣誉和后台字段。关联对象的自动展开不能泄露未发布的队伍、人员资料、内部核验记录或私有链接。

缓存内容不得混入管理员视角或预览内容。预览必须鉴权并禁止进入公开缓存。公开缓存键和失效机制应与内容、权限及时间状态相适配。

记录账号权限变更、发布/撤下、关键配置变更等必要审计事件；日志不记录完整请求体、密码、令牌或私有资料。

## 8. 安全、隐私与资源使用

认证优先使用 CMS 和成熟基础设施的能力。生产 cookie、会话、密码重置和跨站请求防护按实际部署域名正确配置，并覆盖鉴权失败测试。

后台禁用默认公开注册；首次管理员通过受控初始化流程创建，不内置通用账号密码，不把初始秘密打印到 CI 或共享日志中。

`.env.example` 只含变量名、说明和安全示例。真实 `.env`、密钥、数据库导出及私人资料必须被 Git 忽略。测试使用虚构或脱敏数据，不读取生产数据填充测试。

使用富文本白名单和合适的输出处理，阻止任意脚本、危险 URL 与未授权嵌入。外链校验协议，防止危险跳转。不得为了检测报名链接而实现不受限制的服务端 URL 抓取功能。

媒体上传校验体积、扩展名和实际类型；对可执行或主动内容采取拒绝或隔离策略。公开媒体库的含义是文件可以公开访问，草稿页面并不会自动使其中的公开媒体变成保密文件。

配置适当的安全响应头、登录失败限制、可信来源和代理设置。内容安全策略应通过实际前台与后台测试，不能为了“安全分数”把后台编辑或必要资源全部阻断。

生产网站上线前检查域名与主体管理、学校授权、部署地区要求和适用的隐私说明。代码可以先完成，不得把未确认的事项写成“已合规”。

V1 不引入跨站画像、广告追踪或收集个人身份的埋点。需要统计时采用可禁用的第一方最小统计，仅计页面或入口事件；不把用户输入、联系方式或带敏感参数的 URL 写入事件。外部报名点击不能表述为报名成功。

## 9. SEO、性能与内容一致性

实现页面级标题、描述、分享信息、规范地址、仅包含已发布内容的 sitemap，以及合适的 robots 设置。`/admin`、预览和私有接口的保护必须依靠鉴权，不是 robots。

元数据和结构化数据只能使用实际内容。正式域名未知时使用环境变量，不在代码里编造学校域名或实际归属。

图片使用合理尺寸、压缩和延迟加载；首屏关键图片与其余图片采用不同加载策略。相册分页或分批加载，不能一次加载所有原图。

公开页面优先减少客户端 JavaScript。缓存/再验证采用与所选 Next.js 版本一致的实现。发布、撤下、改 slug、变更关联内容时应正确更新相关页面。

活动截止等由时间驱动的展示不能长期停留在旧缓存中。明确设置再验证、服务端状态校验或其他可靠机制，并使用可控时间的测试验证。

记录实际运行环境下的性能与可访问性检查结果，不虚构线上吞吐、并发量、百分位延迟或 Lighthouse 分数。

## 10. 开发、预览、生产与部署

### 10.1 环境分离

使用独立的开发、预览和生产配置、数据库与凭据。明确区分业务部署环境与 `NODE_ENV`：预览环境也可能运行生产构建，不能仅凭 `NODE_ENV=production` 判断是真实生产站。

建议使用显式的 `APP_ENV=development|staging|production`。按实际框架需求设置其他变量并写进 `.env.example`。

演示数据只在开发/预览环境显式导入，不随应用启动自动导入。所有演示资料必须易于识别，可重复导入并按明确标记清理。清理脚本不得删除真实数据。

正式发布检查应阻止演示内容被对外误认成真实社团内容。真实资料不足时，正式站使用空状态或不发布对应栏目内容，不自动拿演示记录替代。

### 10.2 容器与同机多站点

Docker Compose 至少覆盖应用和数据库；反向代理配置按部署方式提供。数据库和媒体文件使用持久化存储。应用尽量使用非 root 身份运行。

数据库不向公网开放。网络、服务名、数据卷和宿主机端口避免与已有项目冲突；本地数据库端口确需开放时限制绑定地址。

已有另一个网站时，本项目提供独立虚拟主机配置片段或独立服务接入方案。未经核验不能占用其端口、覆盖其配置或重启无关服务。

提供存活和就绪检查；就绪检查可以验证必要依赖，但不得返回数据库凭据、环境变量或堆栈细节。

没有服务器权限时完成本地生产构建和容器验证，并明确“尚未部署到线上”。不能把本地容器截图描述为已经上线。

### 10.3 数据库迁移与备份恢复

提交可审查的迁移。生产不使用开发自动同步代替迁移，也不在每次启动时无控制地并发执行迁移。

提供数据库和媒体备份方案、实际脚本与恢复说明。备份应具备明确的执行记录、保留策略、权限限制与异机保存接口，不把同盘复制当作完整灾备。

默认建议每日备份；实际频率、保留天数和异机目的地做成配置。未配置异机目的地时明确记录阻塞，不声称已具备异机备份。

至少用本地测试数据完成一次隔离环境的数据库恢复演练，并检查关键记录与媒体恢复情况。恢复验证不得指向现有真实生产库。

区分应用版本回退和数据结构回退。破坏性迁移需要备份、验证与人工授权，不能承诺任意迁移都能无损撤销。
